## 2. Why `float` is `notried` everywhere (candidate-list prune — deterministic, from the report)

The walk attempts `float` only when the report's `predicted_rel_err_if_float` signal makes it
plausible — the **same** gate the region walk uses (`predicted_rel_err_if_float ≤
error_threshold(tolerance) = 10⁻⁷`, agent.py `_float_rung_ok`). In `report_5k.json`, the worst-case
`predicted_rel_err_if_float` for **every** integral is ≫ 10⁻⁷ (B1 = 0.135, B10 = 1.8e8, B12 = 6.3e14,
…), so float is pruned for all 21 (`regions_flagged_pred_float = 21`). `ff` is always attempted (the
workhorse).

This matches the reference outcome exactly: in `phase2_lmeasure.py` (357a5d7) **float was attempted
and rejected for all 10 raw-double integrals** (float p100 = 2.6–4.2 digits, far under 7.0). The
tu_only walk reaches the same routing more cheaply by pruning the float build up front on the report
signal rather than building+measuring a doomed float TU. **No routing consequence** — float never
wins for any qcdloop box integral at tol 7.0 either way. This is a candidate-list efficiency
difference, deterministic and report-driven, not a Validator/precision difference.

### 3.1 B12 ff→dd — the sample-count difference (real signal)

The reference L-measure ran at **2000 samples** (`phase2_lmeasure_tol7_out/…json: "sample_count":
2000`); this e2e uses the **task-mandated 5000**. B12 is the whole-app global-min hotspot
(project_phase_2e_solver_stage1). Its p100 worst-case is exactly the quantity that deepens as more
samples probe the tail:

| | reference @2000 | this run @5000 |
|---|---|---|
| B12 base (double) | 9.325 | **3.691** |
| B12 ff | 7.944 | **2.406** |
| B12 dd | 15.956 | 14.331 |

At 2000 samples B12's double baseline (9.33) cleared 7.0, so it was a downshift candidate and ff
(7.94) won. At 5000 samples the worse tail sample drags the double baseline to 3.69 (**below** the
bar) and ff to 2.41 (**far** below) — so B12 is now a genuine **correctness** case: only dd (14.33)
clears 7.0, and it routes **dd honestly**. This is the walk doing exactly the right thing on the
harder, higher-sample measurement — the seed/count were held at the mandated 12345/5000 and not
tuned. It is a **measurement-regime** difference between the two runs, not a pipeline discrepancy.

### 3.2 B14/B15/B16/BIN0 dd→double — the documented dd metric artifact (not a regression)

These four are the analytic-zero integrals (`base = 0.000`). Their dd candidate reads **0.000** under
`_min_digits`, so the pure tolerance gate rejects it (0.0 < 7.0) and they fall back to double. This
is **precisely** the metric artifact proven in `357a5d7` §3: the pinned dd oracle
(`~/qcdloop@ddfun_enabled`) ships naive `abs = sqrt(re²+im²)` while the candidate flip TU uses the
`third_party` hypot `abs`; at analytic-zero components (~1e-29) the two roundoff paths differ and
`_min_digits` (called without `ref_scale`) reads bit-disagreement as 0 digits. The **real** dd
candidate is bit-identical to an arithmetic-synced oracle at ~15.96 (357a5d7 §3 proof table).

**Why the reference still routes these dd and this run routes double.** The routing reference
(`357a5d7`, and the Phase-1 landing `project_phase1_landing`) routes B14/B15/B16/BIN0 to dd on the
**GPU-ceiling acceptance criterion** — an analytic-zero integral carries no correct digits to lose,
so it is *assigned* dd as the correctness tier regardless of the degenerate 0.0 metric. The tu_only
walk, by contract, decides purely on `StrategyConfig.tolerance` via `flip_gate` (the task's explicit
"gate decides vs tolerance, fail-loud" framing). A 0.0 candidate cannot clear a 7.0 bar, so the walk
rejects it. **This is a real, expected divergence in acceptance criterion**, surfaced here rather
than papered over:

> **The tolerance gate and the GPU-ceiling criterion disagree on analytic-zero integrals.** For a
> faithful dd routing of B14/B15/B16/BIN0 the metric must stop reading roundoff bit-disagreement as
> 0 digits. Two clean fixes (both noted in `357a5d7` and unchanged here): (a) pass `ref_scale` into
> `_min_digits` so analytic zeros return `MAX_DIGITS` regardless of roundoff path (matches the
> Validator's `_score`), or (b) sync the hypot `abs` onto the `ddfun_enabled` oracle ref. Per the
> task constraint ("do not tune tolerance / do not silently regenerate"), this run reproduces the
> artifact faithfully and reports it — **no metric change was made in this task.**

No genuine dd result degraded: every non-zero-value dd candidate (B12 here) measures ~14–16 digits
as expected. The artifact is confined to the four analytic-zero integrals, exactly as before.
