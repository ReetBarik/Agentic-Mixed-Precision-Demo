**BIN4 needed one more source enrichment (`f12d8bf`, this round).** On `45197be` alone, BIN4/B4m
ff **build-failed with a NEW error** — a direct side-effect of the `operator int()` added in
`45197be`:

```
B4m.h:172: error: ambiguous overload for 'operator==' (operand types are 'ffloat' and 'int')
    if (ql::Imag(r13) == 0) { ... }
```

`ffloat` now had a symmetric `int` conversion in **both** directions (`ffloat(int)` ctor from
`4f21245` + `operator int()` from `45197be`), so `ffloat == 0` was ambiguous between
`operator==(ffloat)` (promote the literal) and built-in `int==int` (demote `*this`). **dd never
hit this** because `dd_math.hpp:82-87` already ships `ddouble`-vs-`double` comparison overloads
that match scalar literals exactly and win; `ff_math.hpp` had no `float` mirror.

Per the "different compiler error → report and stop, don't guess-fix" constraint, this was
surfaced to Reet first; on authorization I authored the mirror (`f12d8bf`): six overloads
`==,!=,<,>,<=,>=` on `float`, mirroring dd exactly. The `int→float` standard conversion on the
argument beats both user-defined conversions, so `ffloat == 0` now resolves unambiguously.
**Blast radius across the whole box tree: a single site (`B4m.h:172`)** — BIN1/2/3 ff already
built clean. With `f12d8bf`, BIN4 ff builds and measures 0.0 (routes double honestly).

## 3. The dd-digit "shift" is a metric artifact, not a regression — proven

**Symptom.** In phase-1 (upshift) this run, the dd candidate for **exactly** the four
analytic-zero integrals (B14/B15/B16/BIN0, `baseline_digits = 0.0`) dropped from **15.96 → 0.00**,
flipping their gate verdict from `accept` to `reject`. Every integral with `baseline > 0` held
its dd candidate at 15.96 to the 4th decimal. Perfect correlation with the analytic-zero regime.

**Root cause — different `dd_complex.hpp` in oracle vs candidate.** The two dd builds source the
header from different places:

- **dd oracle** (the measurement reference): `QL_HEADERS` = git-archived `~/qcdloop@ddfun_enabled`,
  which ships its **own naive** `dd_complex.hpp` (`abs = sqrt(re²+im²)`). `QL_HEADERS` is first
  on the include path, so it wins. The oracle ref is **pinned** and does **not** see `third_party`.
- **dd candidate** (the flip TU): `-I third_party/include` → the **hypot** `dd_complex.hpp` from
  `45197be`.

Before `45197be`, both were naive → **bit-identical** dd roundoff at the analytic-zero components
(true value ~1e-29) → `err = 0` → the metric returns `MAX_DIGITS` = 15.96. After the fix, only
the candidate's arithmetic changed → the two roundoff paths differ at the ~1e-29 noise floor →
`err ≈ true` → **0 digits**. The `_min_digits` reduction calls `precise_digits_fast` **without**
`ref_scale`, so its analytic-zero guard is disabled — it measures bit-agreement of two roundoff
paths, not real precision. The prior 15.96 was **bit-identity luck**, carrying no dd-quality
information (there is no "true value" to be correct about at an analytic zero).

**Proof.** Rebuilt the oracle with the *same* hypot `abs` as the candidate (surgical in-place
patch on the scratch `phase1_lmeasure_out/dd_oracle_tree` copy, preserving its `ql::ddfun`
namespace — never touched the pinned repo) and re-measured:

| integral | dd cand vs **naive** oracle (this run) | dd cand vs **hypot** oracle (proof) |
|---|---|---|
| B14 | 0.000 | **15.958** |
| B15 | 0.000 | **15.963** |
| B16 | 0.000 | **15.960** |
| BIN0| 0.000 | 0.185 |

B14/B15/B16 snap back to bit-identity (15.96) the instant the oracle uses the candidate's
arithmetic; BIN0 lands at 0.18 (its analytic zero sits marginally above the metric's degenerate
floor either way). **No real dd degradation exists** — the candidate is exactly as good as
before; only the reference it's differenced against moved.

**Verdict.** Not a regression under any of the three stated criteria: no previously-accepted dd
tier really dropped below 7.0 (the drop is a reference mismatch), no ff tier dropped, and the
only >1-digit shift is the artifact. The four dd-core integrals **hold at dd** (GPU-ceiling
acceptance, unchanged from `d733c40`).

*Scratch artifacts (`_diag_oracle_sync_remeasure.py`, `dd_build_synced`, the in-place oracle
patch) were removed after the proof; the oracle tree regenerates pristine (git-archived) on the
next real run. Nothing committed from the diagnosis.*

> **Latent flag for Reet (not blocking):** the dd oracle is pinned to `~/qcdloop@ddfun_enabled`,
> which will now diverge from `third_party` at analytic-zero components until the hypot fix is
> also landed on that ref. It doesn't affect routing (the four are dd-core regardless), but the
> phase-1 dd-candidate *number* for those four reads 0.0 rather than 15.96 until the oracle ref
> is synced. Two clean options: (a) mirror the hypot fix onto `ddfun_enabled`, or (b) teach
> `_min_digits` to pass `ref_scale` so analytic zeros return MAX_DIGITS regardless of roundoff
> path (the more robust fix; matches the Validator's `_score` behavior).
