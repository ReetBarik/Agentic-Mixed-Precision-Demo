## 3. STOP #A triage (§2.4 sequence)

The brief's triage sequence, in order:

### 3.1 Is the leaf/chain emission correct? — YES (leaf promotion is not the fault)

The candidate (`4c26e77` on the B10 tierb branch) emits everything the design calls for:

* **`Lnrat_B10`** materialised (the @138 `(TScale,TScale)` shallow overload clone), body
  verbatim, return-widened to `ddcomplex`.
* **`B10_B1m_B10`** variant (the entry integral's body) with `dilog4`/`dilog5` decls widened
  to `quad::ddfun::ddcomplex` and the producing calls rerouted to `Li2omx2_B10_B1m_B10`; the
  cancellation `res(i,0) = dilog4 - dilog5` executes with **ddcomplex operands**.
* `Li2omx2` / `ddilog` return widens (rule c) present; 49 variants declared total.
* **Candidate builds clean** — `[100%] Built target boxGPU_app` (`iter_0_build.log`). The
  clones compile against the enriched source, exactly as the L3 compile gate predicted.

So the ddcomplex-vs-ddouble carrier binding at the `Lnrat_B10` return (the L3-resume §1(c)
caveat) is **correct** — `dilog4`/`dilog5`/`Li2omx2` all land at `ddcomplex`, matching the
box binding `TOutput == Kokkos::complex<double>`. No intervening `TOutput(...)` narrowing
demotes the dd value inside the promoted variant. The emission is sound.

### 3.2 Are the promoted clones actually REACHED at dd at runtime? — NO. This is the fault.

The driver calls `ql::BO<…>(res, …)` (`src/boxGPU_tracked.cpp:191`). The **live** dispatch
`BO` lives in `boxGPU.h:69-143` and routes `massive == 1` to `ql::B1m<…>` (`boxGPU.h:129`).

**`boxGPU.h` is byte-unchanged in the candidate.** The root reroute `B1m → B1m_B10` was
*recorded* (`chain_promote` returns `reroutes = {'B1m': 'B1m_B10', 'B0m': 'B0m_B10', 'B2m':
'B2m_B10'}`) but written to the **wrong `BO`**:

```
graph.defs["BO"] (6 definitions, in libclang order):
  [0] B0m.h:432-496     <- _resolve_root_file / _pick_def BOTH take defs[0]
  [1] B1m.h:332-396
  [2] B2m.h:657-721
  [3] B3m.h:244-308
  [4] B4m.h:272-336
  [5] boxGPU.h:69-143   <- the LIVE dispatch BO (the one the build actually compiles)
```

Each group header (`B0m.h`, `B1m.h`, …) carries a **pruned** `BO` guarded by
`#ifndef QCDLOOP_BOX_FULL_DISPATCH` (`B0m.h:427`). `boxGPU.h:33` does
`#define QCDLOOP_BOX_FULL_DISPATCH` **before** including the group headers, so **all five
pruned `BO` copies are preprocessor-dead**; only `boxGPU.h:69` survives to the compiler.

`chain_promote` calls `_resolve_root_file(graph)` and `_pick_def(graph, "BO")`, both of which
return `defs[0]` = the **pruned, `#ifndef`-dead `B0m.h:432` BO**. The reroute is applied
there (and the pruned B0m BO doesn't even call `B1m` — `BO calls B1m? False`), so:

* the edit lands on dead code (`chain_promote` reports `root_file CHANGED: True`, but it
  changed the dead pruned BO in `B0m.h`, irrelevant to runtime);
* the **live** `boxGPU.h` BO is never touched → runtime path is
  `BO(live) → B1m(original) → B10(original, unpromoted) → Li2omx2(original, double)`;
* the entire promoted tree `B1m_B10 → B10_B1m_B10 → Li2omx2_B10_B1m_B10 → Lnrat_B10` is
  compiled but **unreachable dead code**.

Hence the output is bit-identical to double and `kernel_measured_lift = 0.0`. This is exactly
the §2.4 "a promotion that didn't land / mis-scoped closure" cause — **the dd cancellation
never executes**, so there is nothing for the 43-coeff series to lift.

### 3.3 Is this leaf-promotion's bug? — NO. Pre-existing root-resolution defect.

The `defs[0]`-picks-the-pruned-BO defect is in `_resolve_root_file` / `_pick_def`
(`agents/patcher/fanout.py`), **independent of rule (d)**. It would silently no-op *any*
chain whose correctness depends on the root reroute — but it was **masked** until now because
every prior B10/B12/B13 chain candidate was `apply_failed` (never built). L-measure is the
first run where a B10 chain compiled, so it is the first to expose the dead-dispatch reroute.
B14 does not expose it because B14 is genuinely `chain_no_lift` (dd-sufficient; its floor
13.1855 needs no chain), so its zero lift is *correct* and byte-identical to baseline.

Per the brief this is a **STOP + hand-back, not an L-measure code fix** (it is neither
L1′/L2/L3 machinery nor L-measure's to patch — it is a fan-out root-resolution issue the
leaf-promotion build first surfaced). Candidate fix for Reet's consideration (design only,
NOT applied): `_resolve_root_file` / `_pick_def` must select the BO definition that is *live*
under the app's build defines — e.g. prefer the entry-point definition in the file the driver
includes as the dispatch root (`boxGPU.h`), or the one not guarded by an inactive `#ifndef`,
rather than `defs[0]`. This is the same "which overload is actually reachable" problem
`_select_leaf_overload` already solves for leaf callees (subset match), now needed for the
**root** entry point.

### 3.4 What was NOT the cause (falsifier discipline)

* **Not truncation.** 43-coeff dd `_C` is source-resident (P5); the series tail is ~1e-35,
  below dd's ~1e-32 floor. Coefficient synthesis (Option A / L4) is **not** the answer and
  was not reached for.
* **Not the carrier binding.** `dilog4`/`dilog5`/`Li2omx2` all correctly land at `ddcomplex`
  in the emitted variant (§3.1).
* **Not an intervening narrowing.** The promoted variant body carries dd end-to-end to
  `res(i,0)`; the only truncation is the *designed* exit store to the caller-precision output
  container, which is correct (and would still have shown a lift had the variant run).
